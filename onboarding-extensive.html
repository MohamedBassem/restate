Restate Runtime — Extensive Onboarding

Welcome to the runtime team. This document is an in-depth, evidence-cited tour of the restate codebase. Every claim is anchored to a file and (where useful) a line range so you can verify it yourself and use it as a launchpad for deeper exploration.

Generated from a direct read of this workspace. Workspace version: 1.7.0-dev, Rust edition 2024, MSRV 1.95.0. Cargo.toml:35–38

What Restate is

Restate is a distributed runtime that gives applications five primitives, summarized in the project README:

  • Reliable execution — code runs to completion; failures recover partial progress via durable execution. README.md:98
  • Reliable communication — exactly-once request/response, one-way, scheduled. README.md:99
  • Durable promises & timers — sleep, webhooks, awaitables survive crashes. README.md:100
  • Consistent K/V state — per-entity state persisted atomically with execution progress. README.md:101
  • Suspending user code — code pauses on awaitables; ideal for FaaS. README.md:102

What this means for runtime engineers: there is a single per-partition state machine that is the source of truth, and everything else (invoker, ingress, networking, bifrost) feeds into or out of it. Understanding that loop is the single most important thing you'll do this week.

The hot path of an invocation

A request enters via ingress, lands on the partition that owns its key, and gets driven through a durable state machine:

→
ingress-http
→
partition processor (leader)
→
Bifrost append (Envelope)
→
state machine apply
→
invoker drives SDK

Map: crates/ingress-http → crates/worker/src/partition/ (the PartitionProcessor at crates/worker/src/partition/mod.rs:308) → crates/bifrost/ → crates/worker/src/partition/state_machine/ (StateMachine at crates/worker/src/partition/state_machine/mod.rs:149) → crates/invoker-impl/.

Configuration model

Configuration is a hot-reloadable singleton:

  • Configuration struct is composed of per-subsystem option blocks. crates/types/src/config/mod.rs:267–279
  • Storage is an ArcSwap<Configuration>; Configuration::pinned() gives a fast snapshot. crates/types/src/config/mod.rs:243–256, 315–319
  • The configuration sub-modules are: admin · aws · bifrost · common · dynamodb_store · gossip · http · ingress · invocation · kafka · log_server · metadata_server · networking · object_store · query_engine · rocksdb · worker. crates/types/src/config/mod.rs:14–52
Hard rule: don't hold a Configuration::pinned() reference across .await. The snapshot is built on a limited number of fast slots; holding it across awaits starves the rest of the process. Re-pin after the await. CLAUDE.md (Rust style §4)

TaskCenter

TaskCenter is the supervisor for every long-running task in the process. Spawning anything outside it is a bug. Important properties:

  • Tasks live in named kinds; the kind decides what happens on cancellation (ignore, abort, wait) and on error (log, shutdown). crates/core/src/task_center/task_kind.rs:46–67
  • Many task kinds are runtime-relevant: WorkerRole, PartitionProcessor, PartitionProcessorManager, PartitionSnapshotProducer, BifrostWatchdog, BifrostAppender, BifrostBackground{High,Low}Priority, SequencerAppender, LogletWorker, LogStoreWriter, Shuffle, Cleaner, LogTrimmer, NetworkMessageHandler, ConnectionReactor, ClusterController, FailureDetector, MetadataBackgroundSync, SystemBoot, SystemService. crates/core/src/task_center/task_kind.rs:67–202
  • Tasks are spawned via TaskCenter::spawn_child(kind, name, future). Example: crates/worker/src/lib.rs:220–231

Metadata

Metadata flows through:

  • restate-metadata-store — client API to the store.
  • restate-metadata-server — the server implementation.
  • restate-metadata-providers — pluggable backends.
  • restate-metadata-server-grpc — gRPC surface.

In-process, restate_core::Metadata exposes versioned views: NodesConfiguration (whose Role enum we covered above nodes_config.rs:132–146), partition table, schema, logs metadata, etc. Components consume these via the Live<T>/LiveLoad abstractions in restate-types::live, which allow cheap snapshotting with change notifications.

Coding guidelines

Import order

  1. std
  2. third-party crates
  3. restate_* crates
  4. local crate (self, super, crate)

Blank line between each stanza. cargo fmt must respect this. CLAUDE.md (Rust Code Style §1–2)

Hard rules

  • Never hold a reference from Configuration::pinned() across an .await. CLAUDE.md §4
  • Prefer restate_clock::WallClock over std::time::SystemTime. CLAUDE.md §8
  • Use ByteCount::from(value) when logging byte sizes. CLAUDE.md (style guide)
  • Use KeyRange (re-exported via restate_types::sharding::KeyRange) instead of RangeInclusive<PartitionKey>. CLAUDE.md (style guide)
  • New or deprecated config options must include /// Since vX.Y.Z. CLAUDE.md (style guide)
  • Crate names: hyphenated, prefixed restate-, placed under crates/ without the prefix. docs/dev/rust-guidelines.md:16–17
  • Don't expose channels themselves — go through the Handle or similar. docs/dev/rust-guidelines.md:55
  • Event loops own their channels; don't inject them. docs/dev/rust-guidelines.md:56–70
  • Message ordering is only preserved on a single channel. Two channels between the same pair of components is a race condition. docs/dev/rust-guidelines.md:72–77

Error design

  • Use thiserror for error enums with kind variants.
  • Never Box<dyn Error>; use anyhow::Error only when the caller doesn't need to distinguish variants.
  • Annotate variants with #[code(...)] via CodedError so error pages appear in published docs. Example: worker::BuildError at crates/worker/src/lib.rs:71–95.
  • See restate-errors for the conventions. docs/dev/rust-guidelines.md:81–84

Tests

"Maintenance of unit tests is an overhead we need to keep in check." Add tests for important paths and pack multiple assertions per function rather than splitting them. CLAUDE.md (style guide)

Code style — Less is more

From docs/dev/rust-guidelines.md:

  • Avoid repeating the module name in type names: define Error in invoker, not InvokerError; import as invoker::Error. rust-guidelines.md:10–11
  • Avoid pub/pub(crate) fields except for passive data structs (restate-types) or when fields need to be moved out. Prefer getters/setters. rust-guidelines.md:12–14
  • lib.rs should contain pub re-exports for the crate's public types. rust-guidelines.md:15
  • Cargo.toml: restate-internal deps at the top, others after a blank line, sorted per block. rust-guidelines.md:18

The Restate component pattern

You will see this shape over and over again. Internalize it before reading new code:

// 1) Options — user-configurable, serdeable
#[derive(Serialize, Deserialize, schemars::JsonSchema)]
pub struct Options { /* … */ }

impl Options {
    pub fn build(self) -> Service { Service::new(self) }
}

// 2) Service — owns the event loop and its channels
pub struct Service { /* tx + rx, state, … */ }

impl Service {
    pub fn handle(&self) -> Handle { /* cheap-to-clone */ }

    pub async fn run(self, /* deps */, drain: drain::Watch) {
        // listen on `drain` for graceful shutdown
    }
}

// 3) Handle — the interaction surface; thin wrapper over a channel
#[derive(Clone)]
pub struct Handle { /* … */ }

// 4) Error — thiserror + CodedError where appropriate
#[derive(Debug, thiserror::Error, CodedError)]
pub enum Error { /* … */ }

docs/dev/rust-guidelines.md:36–70

When possible, split into _api (handle + error) and _impl (service). restate-worker + restate-worker-api and restate-invoker-impl are textbook examples. crates/worker/src/lib.rs:58 imports restate_worker_api

Pre-commit validation

Before committing or amending, run (in roughly this order — fast feedback first):

cargo check
cargo nextest run --all-features
cargo fmt --all -- --check
cargo clippy --all-features --all-targets --workspace -- -D warnings

# Only if you touched Cargo.toml / Cargo.lock:
cargo deny --all-features check
cargo hakari generate

CLAUDE.md (Validation Before Committing Changes)

If you rename a trait method, function signature, or public API, search the entire codebase for callers (rg, grep) and update them. The compiler will catch most of it, but generic bounds and feature-gated code can hide breaks. CLAUDE.md (validation section)

Performance discipline

Restate is a high-performance system. Correctness first; performance immediately after. Be especially careful in the latency-critical paths:

  • Bifrost — crates/bifrost/
  • Networking — crates/core/src/network/
  • restate-core — task center, metadata, partitions infra
  • Partition processor state machine — crates/worker/src/partition/state_machine/
  • Invoker — crates/invoker-impl/

CLAUDE.md (Performance Notes)

Allocation hygiene

Prefer passing data by reference. Watch for:

  • Vec / String allocations in tight loops.
  • Cloning Bifrost handles is cheap (Arc), but cloning InvocationRequest bodies is not.
  • Use the niches: Option<NonZeroU32> instead of u32 + sentinel. CLAUDE.md §7

If you're unsure about an optimization's impact, write a Criterion micro-benchmark — that's the team's preferred way to settle these.

docker run --rm -d -p16686:16686 -p4317:4317 \
  -e COLLECTOR_OTLP_ENABLED=true --name jaeger \

docs/dev/local-development.md:86–88

For wire-level debugging, set up Wireshark on loopback, decode the relevant ports as HTTP/2, and load the service-protocol proto contracts. docs/dev/debug.md:12–20

Other helpful tools per the debug doc: grpcurl for sending requests, docker/podman for running SDK containers, a Rust debugger (CLion or rust-analyzer + lldb). docs/dev/debug.md:5–9

Memory profiling

jemalloc heap profiling is compiled in on Linux but inactive by default. Activate at runtime by hitting /debug/heap/activate on the admin port (default 5122), or set MALLOC_CONF. server/src/main.rs:53–57

Your first PR — a survival checklist

  • One concern per PR. Small > clever.
  • Imports in 4-stanza order, blank lines between stanzas. CLAUDE.md §1
  • No Configuration::pinned() references held across .await. CLAUDE.md §4
  • cargo check & cargo nextest run --all-features green.
  • cargo fmt --all -- --check green.
  • cargo clippy --all-features --all-targets --workspace -- -D warnings green.
  • If you touched Cargo.toml: cargo deny --all-features check + cargo hakari generate.
  • New / deprecated config keys carry /// Since vX.Y.Z.
  • Behavior change? Drop a file in release-notes/unreleased/.
  • Test new behavior. Pack multiple assertions per test; don't fragment into many small ones.
  • Commit messages: explain why, not just what. Follow existing repo style — they're usually a single line that reads like a sentence. docs/dev/development-guidelines.md:23–27
  • Rebase onto latest main; the team merges via rebase. docs/dev/development-guidelines.md:17–20
